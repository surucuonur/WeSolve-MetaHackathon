### Per slot

#### `experts` — starting point `muse-spark/kernels/experts/attempt-4`

- **What it is.** One fused per-pair kernel (256 threads per (row, expert-slot) pair, `rows*4` threadgroups), gate/up/down plus silu-mul fused, intermediates in threadgroup memory (3,840 B). Per-block numerics replicate MLX's `affine_gather_qvm` bitwise: strided-lane K accumulation plus `simd_sum` per 32-output block, silu computed entirely in bfloat16 (round after every op). See `muse-spark/kernels/experts/attempt-4/notes.md` and `muse-spark/implementation/hyp-1-fused-experts.md`.
- **Piece timing.** Old grader, independent (Claude re-grade, `claude/findings/muse-round-1.md` §1): candidate 92.1 / 165.4 / 529.9 µs per layer at 1 / 8 / 32 rows against compiled reference 139.5 / 221.4 / 762.4 and reference 143.8 / 222.5 / 770.1 — beats both everywhere when overlapped. Chained (`console-chain.txt`): candidate 132.9 / 175.9 / 587.6 µs per layer against reference 80.3 / 239.6 / 797.6 — **66% slower than the reference at 1 row when chained** (52.6 µs × 20 layers ≈ 1.05 ms per step), faster at 8 and 32 rows. Round 1's own run gave 50.0 / 157.8 / 515.4 µs (independent); the 1-row figure is the outlier Claude already flagged as shifting between runs.
- **G3 effect vs prediction.** Alone in vLLM: +1.16 ms (+21.6%) at 1 request, −0.82 ms (−5.7%) at 8, −4.15 ms (−13.9%) at 32 (`claude/findings/muse-round-1.md` §3). Round 1 predicted (piece basis) −0.29 / −1.22 / −5.01 ms and (knock-out basis) −0.40 / −1.30 / −3.67 ms to −0.5 / −2.5 / −8.6 ms (`muse-spark/summary.md`, `muse-spark/implementation/README.md` *Ready to test*). At 1 request the sign flips: predicted faster, measured slower. At 8 and 32 requests the measured saving is real but smaller than the piece basis. The compiled reference alone changes the step by +0.07 / +0.02 / −0.10 ms, so the attempt beats the compiled reference at 8 and 32 requests and loses to both at 1 request (brief's G3 rule).
  - **Reason (measured).** The old piece timing overlapped the 20 layers' calls, hiding one call's latency. Chained, the kernel's latency shows. Claude's estimate from the code: at 1 row the grid is 4 threadgroups (one per pair), too few to fill the 16-core GPU, so one call takes long even when many calls together go fast. Round 1 called this occupancy starvation; attempt-4 doubled threads per pair to 256 to fight it and still chains slower than the reference at 1 row.
- **What keeps it from passing G2.** Exact at decode sizes only. Under the new grader (`results/runs/2026-11-04-muse-round-1/grade-exact-experts.json`): decode 1 / 8 / 32 rows differ 0 / 0 / 0 (pass); prefill 127 / 1,016 / 2,048 rows differ 4,868,667 / 39,078,912 / 78,741,557 elements, up to 43 / 65 / 110.5 units in the last place (fail). Cause: the kernel copies `gather_qvm`'s arithmetic exactly, which is why it is bit-exact at decode sizes. From 60 rows on MLX switches its experts kernel from `gather_qvm` to `gather_qmm_rhs`, which rounds differently (`claude/findings/muse-round-1.md` §2, §6; dispatch in `muse-spark/exploration/territory-switch-layers.md` §G and `territory-quantized-kernels.md` §C). The grader never tested more than 32 rows in round 1.
- **Where it still spends its time.** The 1-row chained latency above (132.9 vs 80.3 µs per layer). Per-pair weight reads remain: at 32 rows the experts read 908 MB against 443 MB for the distinct experts (GPU counters, `results/runs/2026-11-02-gpu-counters/tables.md` via round 1's analysis), half the bytes repeat reads, and even so the path runs at only 62 GB/s (31% of peak), so most of the cost is kernel efficiency, not bytes. Grouped designs that read each expert once lost in round 1's piece harness (duty-cycle ceiling ~55 GB/s; scan/chunk/barrier overhead) — see *What building taught* in `muse-spark/exploration/README.md`.

#### `routing` — starting point `muse-spark/kernels/routing/attempt-1`

- **What it is.** One fused kernel per layer: router scores (matmul + sigmoid + bias), top-4 selection, weight normalise/scale. One 32-thread threadgroup per row; thread `t` computes experts `t` and `t+32`; thread 0 does the serial top-4 scan. See `muse-spark/kernels/routing/attempt-1/notes.md` and `muse-spark/implementation/hyp-2-fused-routing.md`.
- **Piece timing.** Old grader, independent (Claude re-grade): candidate 25.3 / 24.3 / 68.9 µs per layer against compiled 31.5 / 42.7 / 87.6 and reference 39.9 / 83.5 / 101.2 — beats compiled everywhere. Round 1's own run: 28.5 / 23.6 / 41.8 µs. No chained figure was published for this slot; the new grader's chained timing is what round 2 must beat.
- **G3 effect vs prediction.** Alone in vLLM: +0.19 ms (+3.4%) at 1 request, −0.40 ms (−2.8%) at 8, −0.49 ms (−1.6%) at 32. Round 1 predicted (piece basis) −0.15 / −0.49 / −0.47 ms and (knock-out basis) −0.9 / −1.2 / −1.4 ms. At 8 and 32 requests the measured saving tracks the piece basis, far below the knock-out basis. At 1 request the sign flips. Against the brief's G3 rule the attempt beats both the unchanged model and the compiled reference only at 32 requests; at 8 requests its range ends 0.05 ms below the compiled reference's; at 1 request it is slower than both. The compiled reference alone saves 0.22 / 0.18 / 0.16 ms, so part of the headroom is already taken by compiling the reference.
  - **Reason.** Round 1's builders found the piece harness prices a fused kernel at a ~24 µs per layer floor (dispatch/eval plus, for routing, two barriers and a serial 60-element scan on thread 0), not at one 6.81 µs launch; the reference's 12 kernels cost ~3 µs each when pipelined 20 deep. The knock-out and the piece harness therefore disagree on the slot's standalone cost, and G3 sides closer to the piece harness at 8/32 rows. The 1-row case has a single threadgroup wavefront on a 16-core GPU, so fixed cost amortises worst there.
- **What keeps it from passing G2.** Experts and order match; weights differ in the last bits at every size. Under the new grader (`grade-exact-routing.json`): rows differing 20 / 159 / 638 at decode 1 / 8 / 32 rows (of 20 / 160 / 640 rows summed over 20 layers) and 2,518 / 16,187 / 32,743 at prefill 127 / 1,016 / 2,048 rows; rows with other experts 0 at every size; max relative error 2.6×10⁻⁶ at decode, up to 8.7×10⁻⁶ in the prefill. The old G2 allowed 10⁻⁴ relative, so this passed with ~40× margin in round 1; the new G2 asks for equality in the same order, since combine sums the pairs in that order. Cause (Claude's reading): the reference's order of operations and rounding points for the router product and the weight sum — for example the float32 sum order of `x @ w_router.T` and of `w.sum(...)` — differ from the kernel's serial 768-term accumulation and left-to-right 4-term sum. Greedy decoding turns any such difference into different tokens: within G2's old tolerances this attempt still changed 7 to 9 of 32 sequences in 24 tokens.
- **Where it still spends its time.** Traffic is negligible (~4 MB per step; w_router 184 KB per layer per row read once). The cost is the fused kernel's fixed floor (~24 µs per layer in the old harness) plus the serial top-4 scan. Compute (92k FLOP per row) is negligible either way.

#### `combine` — starting point `muse-spark/kernels/combine/attempt-1`

- **What it is.** One fused kernel per layer: weight the 4 experts' bfloat16 outputs by the float32 weights, sum in float32, round once to bfloat16, add the shared expert. One thread per output element on a `rows×768` grid, threadgroup 256, no threadgroup memory. See `muse-spark/kernels/combine/attempt-1/notes.md` and `muse-spark/implementation/hyp-3-fused-combine.md`.
- **Piece timing.** Old grader, independent (Claude re-grade): candidate 18.6 / 17.0 / 18.9 µs per layer against compiled 23.8 / 26.1 / 32.0 and reference 23.1 / 22.5 / 39.5 — beats compiled everywhere. Round 1's own run: 17.2 / 17.0 / 18.5 µs.
- **G3 effect vs prediction.** Alone in vLLM: −0.51 ms (−9.6%) at 1 request, −0.71 ms (−4.9%) at 8, −0.39 ms (−1.3%) at 32. Round 1 predicted (piece basis) −0.10 / −0.10 / −0.24 ms and (knock-out basis) −0.47 / −0.30 / −0.19 ms. The measured saving exceeds the piece basis at 1 and 8 requests and sits between the two bases at 32. Against the brief's G3 rule the attempt beats both the unchanged model and the compiled reference at 8 requests; at 1 request its range overlaps the compiled reference's; at 32 requests it is 0.12 ms ahead, within the spread. The compiled reference alone saves 0.29 / 0.26 / 0.27 ms.
- **What keeps it from passing G2.** A handful of elements differ from 8 rows on. Under the new grader (`grade-exact-combine.json`): decode 1 row differ 0 (pass), 8 rows differ 2 (max 2.0 ULP), 32 rows differ 2 (max 1.0 ULP); prefill 127 / 1,016 / 2,048 rows differ 6 / 50 / 130 elements, up to 1 / 16 / 32 ULP (fail). The old G2 allowed 2 ULP, so this passed in round 1 (the 8-row 2.0-ULP touch was proven to be Metal FMA contraction of the mul+add chain, max exactly 2.0 on realistic inputs). The new G2 asks for every element equal. Cause (Claude's reading): the reference's order of operations for the sum over the 4 pairs — the candidate's left-to-right chain contracts to FMAs while MLX's `col_reduce_small` reduction associates differently — so a few elements round differently. The fix must reproduce the reference's association and rounding points, and suppress contraction where it changes the result.
- **Where it still spends its time.** At the bare dispatch floor (~17 µs per layer, flat across row counts; traffic ≤1.4 µs at 200 GB/s). Both round-1 combine directions sit on this floor; no kernel-body change in round 1 moved it.

#### All three together

In vLLM all three attempts together change the step by +0.98 ms (+18.3%) at 1 request, +0.16 ms (+1.1%) at 8, −1.76 ms (−5.9%) at 32, against round 1's prediction of −0.54 / −1.81 / −5.72 ms. The parts do not add: at 8 requests the three alone save 0.82, 0.40 and 0.71 ms but together cost 0.16 ms; at 32 requests the experts kernel alone saves 4.15 ms and all three together save 1.76 ms. Together they launch 567 kernels per step at 1 request against 967 unchanged, so a shorter list of kernels runs slower. **Measured but not explained** in Claude's measurement; the cause is an open question for round 2 (see territory `g3` below). The three compiled references together save 0.50 / 0.56 / 0.24 ms in vLLM (0.62 / 0.52 / 0.26 ms in plain MLX) without any new kernel.

In the model every attempt changes tokens: with 32 requests in vLLM each one alone changes 7 to 12 of the 32 sequences from the first generated token, and all three together change 13. The compiled references change none, so the unchanged model is deterministic and every difference comes from the attempts. The experts cause is the prefill (above); routing's and combine's small rounding differences, within the old G2 tolerances, are enough to flip greedy tokens on these near-tie prompts.

Round 1 ran the grader 29 times on the experts slot for the 4 attempts its summary counts, 18 of those on attempt-1 (editing the same folder between runs). Skill version 5 keeps the rule that one grader run is one attempt.

### What is left

Confirmed inefficiencies not yet built or not fully removed, ranked by predicted saving against the compiled reference (no slot has a baseline, so the reference is the bar). Savings are the headroom the starting point leaves: the chained piece gap where Claude measured it, otherwise the G3 gap to the compiled reference. Exactness is listed first where it blocks the slot entirely — a faster kernel that fails G2 saves nothing.

1. **Experts: exact at prefill sizes, and faster chained at 1 row.** The slot is 0.92 ms of a 4.75 ms step at 1 row and 14.67 ms of 28.19 ms (52%) at 32 rows (Claude's knock-outs, round 1 analysis). The starting point already beats the compiled reference when overlapped at all rows and chained at 8/32 rows, but it (a) fails G2 at every prefill size because it matches `gather_qvm` while MLX runs `gather_qmm_rhs` from 60 rows on, and (b) loses 52.6 µs per layer chained at 1 row (≈1.05 ms per step, matching G3's +1.16 ms). Removing (a) is a correctness gate, not a saving; removing (b) is worth up to ~1.1 ms per step at 1 request against the reference, on top of keeping the 8/32-row chained wins (63.7 and 210.0 µs per layer against the reference). This is Claude's questions 1 and 2 for round 2.
2. **Routing: exact float32 arithmetic.** The slot costs 1.02 ms at 1 request and 1.68 ms at 32 (knock-outs); the starting point's G3 headroom over the compiled reference is negative at 1 request (+0.19 against the compiled reference's −0.22 ms) and small at 8/32. The blocker is exactness: every row's weights differ in the last bits while the experts and their order already match. Reproducing the reference's sum orders and rounding points (the router product, the sigmoid, the 4-term normalise sum) makes the slot pass G2; only then can a chained-timing win over the compiled reference be banked. Claude's question 3 (routing half).
3. **Combine: exact 4-term sum.** The slot costs 0.61 ms at 1 request and 0.33 ms at 32. The starting point differs in only 2 elements at decode 8/32 rows and 130 at the largest prefill size — the smallest exactness gap of the three — from FMA contraction against the reference's reduction order. Reproducing that order (and suppressing contraction, e.g. with a `precise` accumulator, an option round 1's boundary check already named) should make the slot pass G2 with the kernel otherwise unchanged, keeping its G3 win at 8 requests and contesting 1 and 32. Claude's question 3 (combine half).
4. **Why the three together lose time each saves alone.** At 8 requests in vLLM the three alone save 1.93 ms in sum and together cost 0.16 ms; at 32 requests the experts alone save 4.15 ms and together 1.76 ms. No slot's kernel explains the interaction; it is measured but not explained. Until it is understood, per-slot piece wins may not compose into a G3 win. Claude's question 4.
