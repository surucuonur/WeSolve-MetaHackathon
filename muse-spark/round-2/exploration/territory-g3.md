## What it does

This territory is not code in the decode step. It is the measurement that decides whether round 1's three final attempts (`experts/attempt-4`, `routing/attempt-1`, `combine/attempt-1`) actually made the model faster: Claude's re-grading, the chained-vs-independent timing experiment, and the end-to-end token + step-period (G3) runs in plain MLX and vLLM, all written up in [claude/findings/muse-round-1.md](../../../claude/findings/muse-round-1.md) with raw data in `results/runs/2026-11-04-muse-round-1/`. Its question for round 2 is where the end-to-end change differs from the piece timing, and why.

### 3. Chained vs independent piece timing (`bench/micro/chain_timing.py`, `console-chain.txt`)

- **Callers:** Claude's experiment of 2026-11-04, run as `.venv/bin/python bench/micro/chain_timing.py muse-spark/kernels/experts/attempt-4` ([chain_timing.py:12](../../../bench/micro/chain_timing.py)); output is `results/runs/2026-11-04-muse-round-1/console-chain.txt`.
- **Callees:** `slots.load_inputs` / `load_expert_weights` for the 20 captured layers; the reference (`slots.ref_experts`) and the attempt loaded by `check_candidate.load`. Two modes per row count ([chain_timing.py:43-60](../../../bench/micro/chain_timing.py)): *independent* — the 20 calls share no data, one `mx.eval(outs)` at the end, as the old grader timed; *chained* — each call's `x` is the previous call's `y[:, 0, :]`, a real data dependency, so a call cannot start before the previous one finishes. Median of 32 repeats, first 2 dropped ([chain_timing.py:59](../../../bench/micro/chain_timing.py)).
- **Data:** µs per layer, reference / attempt-4. Independent: 86.0 / **61.0** at 1 row, 219.1 / **165.1** at 8, 767.3 / **535.0** at 32. Chained: 80.3 / **132.9** at 1, 239.6 / **175.9** at 8, 797.6 / **587.6** at 32 (`console-chain.txt`, all six lines; [muse-round-1.md:118-119](../../../claude/findings/muse-round-1.md)).
- **Neighbours:** in the model the chain is real: layer *n*+1's routing takes layer *n*'s combine output (via the residual stream, `mobilemoe.py:217-232` through `slots.make_moe_call`). The new grader's `link` kernel reproduces this ordering for every slot (piece 2); ADR 0010 records that the chained times match a real data chain within 10%, and that `mx.depends` does not wait (46 µs/layer at 1 row, as fast as no dependency, vs 133–195 µs chained).
- **Cost:** at 1 row the attempt goes from 29% faster than the reference independent ((86.0−61.0)/86.0) to 66% slower chained ((132.9−80.3)/80.3). The chained gap is +52.6 µs/layer × 20 layers = **+1.052 ms/step**, against G3's measured +1.162 ms in vLLM and +1.228 ms in plain MLX (piece 5/6) — the chain explains the 1-request experts slowdown to within 0.11–0.18 ms. At 8 / 32 rows the chained gaps are −63.7 / −210.0 µs/layer = −1.274 / −4.200 ms/step, the same sign and rough size as G3's experts-alone −0.817 / −4.154 ms (vLLM).
- **Invariants:** only the experts slot and only attempt-4 were measured this way. No chained figure exists in this data for routing or combine; any claim about their in-step latency is inference from G3, not a piece timing. Attempt-4's grid is `rows*4` threadgroups of 256 threads (`muse-spark/kernels/experts/attempt-4/spec.json`), i.e. 4 threadgroups at 1 row — Claude's occupancy estimate for the chained latency ([muse-round-1.md:123](../../../claude/findings/muse-round-1.md)) is an estimate from the code, not a counter measurement.

### 4. The G3 harness (`bench/grader/time_candidates.py`)

- **Callers:** Claude's runs producing `console-plain.txt`, `console-vllm.txt`, `muse-plain.jsonl`, `muse-vllm.jsonl` in `results/runs/2026-11-04-muse-round-1/`; invoked as `time_candidates.py plain|vllm <out> experts=<attempt-4> routing=<attempt-1> combine=<attempt-1>` ([time_candidates.py:16-17](../../../bench/grader/time_candidates.py)).
- **Callees:** `Variants` ([time_candidates.py:72-96](../../../bench/grader/time_candidates.py)) installs, per slot, the attempt (`muse-<slot>`), the slot's reference under `mx.compile` (`compiled-<slot>`), and — with several slots given — `muse-all` and `compiled-all`, by replacing `MoE.__call__` in every layer via `slots.make_moe_call`. Token checks: `plain_checks` (24 greedy tokens after 128-token prompts, 1 and 32 requests, [time_candidates.py:98-120](../../../bench/grader/time_candidates.py)) and `rf.vllm_checks` ([repeat_fixes.py:174-224](../../../bench/micro/repeat_fixes.py)). Timing: `rf.time_variants` ([repeat_fixes.py:276-343](../../../bench/micro/repeat_fixes.py)) — settings (1, 128), (8, 128), (32, 128) requests/prompts, 3 repeats shuffled per repeat (`random.Random(100+rep)`, [repeat_fixes.py:290-293](../../../bench/micro/repeat_fixes.py)), 256 generated tokens per run (`--tokens` default 256, [time_candidates.py:135](../../../bench/grader/time_candidates.py)), period = median decode-step period from `breakdown.py`'s recorder; the printed change is the median of the 3 repeat medians against `base`, with the repeats' range as the spread.
- **Data:** one `check` record and 27 `run` records (9 variants × 3 row counts × 3 repeats, per engine) in each `muse-*.jsonl`. Kernel counts come from `count_ops` ([repeat_fixes.py:136-143](../../../bench/micro/repeat_fixes.py)): the exported graph of one decode step, view ops excluded — a count of graph ops, where each `mx.compile` region and each custom kernel counts once. It is not a launch trace.
- **Neighbours:** G3's rule (brief, *How each attempt is judged*): an attempt must beat both the unchanged model and its compiled reference, by more than the spread between repeats. `compiled-all` is the control that shows what `mx.compile` of the untouched references already saves with no new kernel.
- **Cost:** the harness itself is not in the step. Machine caveat for every absolute number below: another job of surucuonur's was running and 21.3–22.7 GB of swap were in use; Docker was quit; vLLM ran with `VLLM_METAL_KV_COMMIT_PROBE=0` ([muse-round-1.md:19](../../../claude/findings/muse-round-1.md)). Shuffled repeats make variant-vs-variant comparisons usable; absolutes carry that caveat.
- **Invariants:** prompts for the token check are random tokens (`mx.random.seed(rows)` + `randint(0, 100000, (rows, 128))` in plain, [time_candidates.py:107-108](../../../bench/grader/time_candidates.py); `random.Random(7)` + `randrange(1000, 100000)` in vLLM, [repeat_fixes.py:179-185](../../../bench/micro/repeat_fixes.py)) — near-tie next-token margins are expected, which is why last-bit differences flip tokens (piece 7). Timing runs use their own seeds (`rows*10000+prompt`, [repeat_fixes.py:299](../../../bench/micro/repeat_fixes.py)), so the timed sequences are not the checked sequences.

### 5. G3 alone and together — plain MLX (`console-plain.txt`, `muse-plain.jsonl`)

- **Callers:** `time_candidates.py plain` (piece 4).
- **Data:** base step 4.998 / 13.541 / 28.496 ms at 1 / 8 / 32 requests (`console-plain.txt` summary block; `muse-plain.jsonl` `run` records, median of 3 repeat medians). Changes against base: experts +1.228 / −0.832 / −3.661 ms; routing +0.233 / −0.361 / −0.318; combine −0.857 / −0.753 / −0.406; **muse-all +0.927 / +0.881 / −1.560**; compiled-all −0.617 / −0.524 / −0.255. Kernel counts at 1 request: base 866, muse-experts 746, muse-routing 666, muse-combine 786, muse-all 466 (`muse-plain.jsonl` `check` records, rows 1); at 32 requests: base 986, muse-all 466.
- **Cost / the additivity test:** the three alone sum to +0.604 / −1.946 / −4.385 ms; together measure +0.927 / +0.881 / −1.560 ms. The interaction (together − sum of alone) is **+0.323 / +2.827 / +2.825 ms**, i.e. +16.1 / +141.3 / +141.2 µs per layer. Adding routing+combine to experts-alone costs −0.301 / +1.713 / +2.101 ms (muse-all − muse-experts) where alone they promise +0.233−0.857 / −0.361−0.753 / −0.318−0.406 ms.
- **Invariants:** kernel-count reductions are exactly additive here: −120 (experts) −200 (routing) −80 (combine) = −400 = 866−466 at 1 request; −240 −200 −80 = −520 at 32 requests. The time is not additive while the count is — the fact any explanation must meet.

### 6. G3 alone and together — vLLM (`console-vllm.txt`, `muse-vllm.jsonl`)

- **Callers:** `time_candidates.py vllm` (piece 4).
- **Data:** base step 5.370 (5.320–5.452) / 14.363 (14.327–14.475) / 29.851 (29.657–29.952) ms (`console-vllm.txt` summary block). Changes: experts **+1.162 (+21.6%)** / −0.817 / −4.154; routing +0.185 / −0.397 / −0.490; combine −0.514 / −0.705 / −0.390; **muse-all +0.980 (+18.3%) / +0.163 (+1.1%) / −1.756 (−5.9%)**; compiled-all −0.498 / −0.558 / −0.242 — all against round 1's prediction of −0.54 / −1.81 / −5.72 ms ([muse-round-1.md:80-91](../../../claude/findings/muse-round-1.md)). Kernel counts at 1 request: base 967, muse-experts 847, muse-routing 767, muse-combine 887, muse-all **567** (`muse-vllm.jsonl` `check` records, rows 1); at 32 requests: base 1087, muse-all 567.
- **Cost / the additivity test:** the three alone sum to +0.833 / −1.919 / −5.034 ms; together measure +0.980 / +0.163 / −1.756 ms. Interaction: **+0.147 / +2.082 / +3.278 ms** (+7.4 / +104.1 / +163.9 µs per layer). Adding routing+combine to experts-alone costs −0.182 / **+0.980** / **+2.398 ms**. The compiled references, the control, compose near-additively: their alone changes sum to −0.442 / −0.419 / −0.532 ms against compiled-all's measured −0.498 / −0.558 / −0.242 ms (interaction −0.056 / −0.139 / +0.290 ms) — so the non-additivity is a property of the three custom kernels together, not of replacing three slots at once. At 1 request the vLLM interaction (+0.147 ms) is the size of the base spread (5.320–5.452 = 0.132 ms); at 8 and 32 requests it is 15–25× the spread and repeats in plain MLX (piece 5), so it is not repeat noise.
- **Invariants:** same additive kernel counts as plain: −120 −200 −80 = −400 at 1 request, −240 −200 −80 = −520 at 32. The headline form: **567 kernels/step run slower than 967 at 1 and 8 requests** — kernel count is not the step's cost driver here.

### 7. Token divergence (`check` records, both engines)

- **Callers:** `plain_checks` / `vllm_checks` (piece 4): 24 greedy tokens, 128-token prompts; a sequence *differs* if any of its 24 tokens differs from base's, with `first_differ_step` the first such token ([repeat_fixes.py:227-234](../../../bench/micro/repeat_fixes.py)).
- **Data:** sequences differing of 32 at 32 requests — plain MLX: experts 19 from token 0, routing 7 from token 1, combine 5 from token 2, muse-all 19 from token 0; vLLM: experts 12, routing 9, combine 7, muse-all 13, all from token 0 (`muse-plain.jsonl` / `muse-vllm.jsonl` `check` records rows 32; [muse-round-1.md:58-62](../../../claude/findings/muse-round-1.md)). At 1 request plain MLX each single attempt differs in its 1 sequence from token 2 while muse-all is exact; vLLM at 1 request every variant is exact — the two engines use different check prompts (piece 4), so the 1-request outcomes are prompt-dependent near-tie flips, not a disagreement about the kernels. Every `compiled-*` variant is exact in both engines at both row counts: the unchanged model is deterministic, and every difference comes from the attempts.
- **Neighbours:** divergence has two measured causes, by slot: the experts attempt is bit-exact at decode sizes but differs in 62% of prefill outputs (piece 2), and the prefill (127–2,048 rows) runs before the first decode step, so its difference is present from token 0; routing's (≤8.7×10⁻⁶) and combine's (≤2 ULP at decode) last-bit differences flip near-tie greedy choices within a few tokens ([muse-round-1.md:66-72](../../../claude/findings/muse-round-1.md)).
- **Cost:** divergence is a correctness verdict (the brief's end-to-end G2), not a timing input: the timed runs generate their own 256 tokens per variant (piece 4), and each slot's per-step cost is data-independent in shape (fixed grids in all three `spec.json` files; the experts attempt reads one expert's weights per (row, slot) pair whichever expert is chosen), so differing tokens do not by themselves change what a step costs. They cannot explain piece 5/6's interaction.
- **Invariants:** `first_differ_step` 0 at 32 requests for experts/muse-all in both engines is the prefill signature; routing/combine first differ at step ≥0 only where their decode/prefill rounding reaches the logits — the counts, not the step, are the stable part across engines.

## Where the end-to-end change differs from the piece timing, and why

Three separate gaps, in the order the measurement establishes them:

1. **Experts at 1 request: piece says faster, step says slower — explained.** Independent piece timing: attempt 29% faster than the reference (61.0 vs 86.0 µs/layer, piece 3) and 92.1 vs 139.5 µs against the compiled reference in the re-grade (piece 1), a promised −0.948 ms/step. G3: **+1.162 ms (vLLM) / +1.228 ms (plain)** against base — the "1.2 ms" slowdown. Chained piece timing reverses the piece sign: 132.9 vs 80.3 µs/layer, +1.052 ms/step, matching G3 to 0.11–0.18 ms. Cause (estimate from the code, [muse-round-1.md:123](../../../claude/findings/muse-round-1.md); kernel side owned by `baseline-experts`): the attempt launches `rows*4` threadgroups of 256 threads — 4 threadgroups at 1 row on a 16-core GPU — so one call's latency is long, and the old timing hid exactly that latency by overlapping the 20 layers' calls. Posted as [ineff-g3-2](ineff-g3-2.md).
2. **Per-slot piece-vs-step gaps at 1 request, routing and combine — measured as gaps, cause not yet timed.** Routing's piece promises −0.124 ms/step against the compiled reference (piece 1); in vLLM it measures +0.185 against base where the compiled reference measures −0.220, i.e. **0.405 ms/step slower than the compiled reference in-step**, a 0.529 ms/step swing from the piece figure. Combine goes the other way: piece −0.104 ms/step, in-step −0.514 against base vs −0.288 compiled (vLLM), over-delivering. No chained routing/combine timing exists in this data (piece 3), so neither gap has a measured cause; the new grader's chained timing (piece 2) is the instrument that will produce one. Noted for `baseline-routing` / `baseline-combine` below; no inefficiency posted from G3 alone.
3. **All three together: slower than each alone predicts — measured, not explained.** Kernel reductions add exactly (pieces 5/6); time does not. The interaction is +0.15 / **+2.08** / **+3.28 ms** (vLLM) and +0.32 / **+2.83** / **+2.83 ms** (plain) at 1 / 8 / 32 requests, while the compiled references together stay within ±0.29 ms of additive. Equivalently: bolting the routing+combine attempts onto the experts attempt *costs* 0.98 ms at 8 requests and 2.40 ms at 32 (vLLM) where those two alone *save* 1.10 and 0.88 ms. What the data rules out: kernel count (additive, and fewer), token divergence (cost is shape-fixed, piece 7), repeat noise (15–25× the spread at 8/32, both engines), and the compiled-reference path (additive). What remains consistent with the numbers, in order: (a) each fused custom kernel carries a serial per-call latency that the 20-layer overlapped piece timing hid and that only fully serialises when all three sit on the same layer chain — the experts instance of this *is* measured (gap 1), and routing shows the same sign at 1 request (gap 2); (b) an interaction between the three custom kernels' execution (occupancy, cache or dispatch behaviour) that no single-slot run excites. The measurement that separates (a) from (b) — pairwise G3 (`experts+routing`, `experts+combine`, `routing+combine`; `time_candidates.py` builds `muse-all` for any subset, [time_candidates.py:85-87](../../../bench/grader/time_candidates.py)) and chained piece timings for routing/combine under the new grader — has not been run; explorers do not run GPU jobs, so it is left as the entry's predicted test. Posted as [ineff-g3-1](ineff-g3-1.md) with the interaction itself as the cost.
